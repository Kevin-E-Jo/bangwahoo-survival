씬 지도 — 병렬 작업의 경계선

민트는 Next.js 페이지, 코랄은 Phaser 캔버스 안의 씬이다. 이 색 경계가 곧 작업을 나눌 수 있는 지점이다.

Next.js 페이지 Phaser 씬

라우트 & 경계 원칙

/login → /town → /play(Phaser 마운트, BootScene부터 시작) → 클리어·사망 시 다시 /town. Next.js와 Phaser는 같은 세션 쿠키로 인증되어 있으므로, 경계를 넘을 때 JS 객체를 직접 넘기지 않는다 — 각자 필요한 데이터를 서버 API로 다시 조회한다. 자세한 계약은 아래 「씬 간 인터페이스」 참고.

Contracts

씬 간 인터페이스

Next.js와 Phaser 사이에 JS 객체를 직접 넘기지 않는다. 아래 API로만 통신하고, 나머지는 각자 영역 안에서 해결한다.

엔드포인트호출 주체역할
GET /api/town/progressTownScene재화·무기 레벨·보유 파츠 조회
POST /api/town/upgradeTownScene업그레이드 구매 — 서버가 재화 검증 후 차감
POST /api/run/startBootScene서버가 seed 발급 — 클라이언트가 유리한 seed를 고르지 못하게 함
POST /api/run/submitResultSceneseed+결과 제출 → 서버가 동일 seed로 재계산해 검증 후 반영

Phaser 내부 이벤트 (DungeonScene ↔ UIScene)

UIScene은 launch()로 DungeonScene과 병렬 실행되므로, 씬 이벤트로만 통신한다.

이벤트페이로드의미
combat:hp-changed{current, max}HP 바 갱신
combat:ammo-changed{current, max}탄약 표시 갱신
combat:wave-started{waveIndex, totalWaves}웨이브 진행도 표시
combat:wave-cleared{waveIndex, loot}웨이브 클리어 연출·획득 표시
combat:run-ended{result, collectedItems, wavesCleared, elapsedMs}ResultScene 전환 트리거

시드 & 검증 로직 공유

라운드 구성(적 수)·보상을 seed로부터 결정하는 함수는 클라이언트(Phaser)와 서버(API route)가 같은 TypeScript 모듈을 import해서 써야 한다. 로직이 갈라지면 서버 재계산이 클라이언트 결과와 어긋나 정상 플레이도 검증에 실패할 수 있다.

Core loop

게임플레이 규칙

루프

업그레이드 시스템 — 런 한정 빌드 강화 (설계 확정 · 구현 대기)

다른 로그라이크처럼, 런 진행 중에 강화를 골라 그 런만의 빌드를 만드는 시스템. 첨삭을 거쳐 세부까지 확정됐고, 아직 코드는 한 줄도 안 들어간 상태다. 마을에서 재화로 사는 영구 업그레이드(탄환 위력·탄창 용량)와는 완전히 별개이며, 런이 끝나면 초기화된다.

선택 시점 & 흐름 확정

기존에 이미 있는 라운드 클리어 흐름(combat:wave-cleared → 600ms 뒤 다음 라운드)에 선택 단계를 끼워 넣는다. 런당 3회로 확정 — 전투가 늘어지는 걸 피하려고 라운드 수를 늘리거나 라운드 중간 픽업을 섞지 않기로 함.

시점선택지비고
런 시작 직후3장 중 1장BootScene → DungeonScene 전환 직후, 첫 라운드 스폰 전에 삽입
1라운드 클리어 후3장 중 1장기존 clearCurrentRound()의 딜레이 지점에 끼워 넣음
2라운드 클리어 후3장 중 1장3라운드(엘리트 등장) 진입 직전 — 마무리 빌드 완성 지점

선택 UI가 뜨는 동안 DungeonScene은 scene.pause()로 정지, 선택 완료 시 재개 — 기존 UIScene과 같은 패턴(병렬 launch + 이벤트)으로 새 씬(가칭 UpgradeChoiceScene)을 추가하는 안을 제안한다. 연출은 그 시절 테마로 확정 — 평범한 카드 3장 나열이 아니라, 가챠캡슐(gacha_capsule 아이템으로 이미 있음) 3개가 놓여있다가 고른 캡슐이 열리며 내용물이 드러나는 식의 연출을 제안. 아트·애니메이션 작업이 추가로 필요하다.

카테고리 개요

발사 패턴계

멀티샷 · 더블샷 · 도탄

  • 총알이 나가는 방식 자체를 바꾼다 — 시각적으로도 가장 화려한 카테고리
스탯 강화계

데미지 · 공속 · 이동속도 · 탄창 · 재장전

  • 수치만 올라가는 안전한 카테고리 — 매 선택지 풀의 "무난한 선택"으로 항상 섞어 넣는다
속성탄계

폭죽·물풍선·찌릿·바람개비·얼음땡·자석·불량식품·플래시·호루라기 (9종)

  • 명중 시 부가 효과 부여 — 적 데이터에 상태(status) 필드가 새로 필요한 유일한 카테고리

발사 패턴계 상세

이름은 이 프로젝트의 "그 시절" 톤에 맞춘 1차 초안 — 아이템 카탈로그의 구슬·팽이·요요·딱총처럼 실제 있던 놀이·문방구에서 따왔다. 마음에 안 들면 언제든 갈아엎어도 되는 부분.

고무줄 연사 Multishot

  • 발사할 때마다 총알 개수 +1, 부채꼴로 균등 확산(각도 간격 15°)
  • 스택 가능 — 최대 3회 중첩(기본 1발 → 최대 4발)
  • 확산이라 개별 총알 명중률은 떨어짐 — 물량으로 커버하는 방향

쌍딱총 Double Shot

  • 멀티샷과 달리 확산 없이, 같은 방향으로 정확히 겹쳐서 1발 더 발사(약 80ms 지연)
  • 스택 불가(유니크) — 명중률 손해 없이 화력만 2배가 되는 대신 흔치 않게
  • 고무줄 연사와는 서로 곱연산(스택마다 총알 수를 배로 늘리는 게 아니라 "동시 발사 세트" 자체를 한 번 더 쏘는 것)으로 상호작용 — 구현 시 발사 함수를 "이번에 만들 총알들의 각도 배열"로 리팩터링해두면 두 효과가 자연스럽게 합성된다

비석치기 Ricochet 확정

  • 총알이 엄폐물에 맞아도 파괴되지 않고 반사각으로 튕겨 계속 날아간다(전통 놀이 "비석치기"에서 이름을 땀) — 튕긴 뒤에도 적에게 명중하면 그대로 데미지
  • 스택 가능 — 스택마다 튕길 수 있는 최대 횟수 +1(최대 2스택 = 2회까지 튕김), 그 이상은 소멸
  • 구현 메모: 현재 physics.add.collider(bullets, obstacles, ...)가 무조건 bullet.destroy()하는 부분을, 이 업그레이드 보유 여부에 따라 반사(속도 벡터를 충돌면 기준으로 반사)로 분기해야 함

스탯 강화계 상세

전부 최대 5스택으로 상한 확정(런당 선택 기회가 3회뿐이라 사실상 초과할 일은 적지만, 안전장치로 둔다).

속성탄계 상세 확정 — 9종 전부 채택

스택형으로 확정 — 여러 속성탄을 동시에 들고 있으면 명중 시 전부 함께 적용된다(서로 상쇄 없음, 각자 독립 작동). 같은 속성을 여러 번 고르면 그 속성 자체도 최대 3스택까지 중첩 가능. 효과 종류가 서로 겹치지 않도록 설계했다 — 지속딜(폭죽·불량식품), 이동 방해(물풍선·얼음땡), 위치 조작(바람개비·자석), 회피용 디버프(플래시·호루라기), 즉발 연쇄(찌릿) 순으로 전부 다른 성격.

🔥 폭죽탄 Fire

  • 명중 시 화상 부여 — 초당 데미지 4, 기본 지속 3초(스택마다 +1초, 최대 5초)
  • 이미 화상 걸린 대상을 다시 맞히면 지속시간만 최댓값으로 갱신(틱 데미지는 안 늘어남)

💧 물풍선탄 Water

  • 명중 시 이동속도 -40%, 기본 지속 2초(스택마다 +0.5초, 최대 3.5초)
  • 여러 발 맞혀도 지속시간만 갱신 — 감속률(-40%) 자체는 스택으로 안 늘림

⚡ 찌릿탄 Electric

  • 명중 시 인접 적 1체에게 50% 데미지로 연쇄(스택마다 +10%p, 최대 3스택 = 70%)
  • 비석치기(도탄)와는 트리거가 다름 — 도탄은 엄폐물에 튕기고, 이건 명중 즉시 인접 적으로 튐. 서로 배타적이지 않고 공존·궁합 좋은 조합으로 취급

💨 바람개비탄 Wind

  • 명중 시 넉백 40px(스택마다 +10px, 최대 3스택 = 60px)
  • 엄폐물 쪽으로 밀어붙이면 잠깐 갇히는 효과도 자연히 남 — 별도 로직 불필요

🧊 얼음땡탄 Ice

  • 명중 시 25% 확률로 0.6초 완전 정지(스택마다 확률 +5%p, 최대 3스택 = 35%; 지속시간은 고정)
  • 물풍선탄(슬로우, 확정 적용)과 달리 확률형 강한 스턴이라 성격이 다름 — 지속시간을 늘리지 않아 물풍선탄의 상위호환이 되지 않게 함

🧲 자석탄 Magnet

  • 명중 지점 반경 80px 안의 다른 적들을 그 지점으로 끌어당김(스택마다 반경 +20px, 최대 3스택 = 120px)
  • 고무줄 연사·비석치기 등 광역기와 조합 시너지가 큼 — 단독보다 조합 의존도가 높은 픽

🤢 불량식품탄 Poison

  • 명중 시 중독 1스택 부여, 스택마다 초당 데미지 2(최대 5중독스택 = 초당 10), 중독 지속 3초(다시 맞으면 스택 +1 및 지속시간 갱신)
  • 폭죽탄(비누적, 고정 틱딜)과 달리 맞을수록 강해지는 지속딜 — 같은 "불 계열" 카테고리 안에서도 성격이 다른 선택지

📸 플래시탄 Flash

  • 명중 시 1.5초간 실명 — 적이 추적을 잃고 무작위 방향으로 이동(스택마다 +0.3초, 최대 3스택 = 2.1초)

구현 순서 제안

9종을 한 번에 다 구현하기보다, 확정된 발사 패턴계·스탯 강화계와 함께 우선 폭죽탄·물풍선탄·찌릿탄 3종으로 먼저 붙여보고(적 상태 필드·틱 처리 루프의 기본 구조를 검증), 나머지 6종은 그 구조 위에 순차로 얹는 방향을 제안한다. 설계 자체는 9종 전부 확정 — 구현 순서만의 문제다.

서버 검증과의 관계

이 업그레이드들은 순수하게 런 안에서만 전투력에 영향을 준다 — 재화·아이템 보상은 여전히 roundsCleared(몇 라운드를 깼는지)만으로 결정되고, 서버는 그 값에 대응하는 보상만 재계산해 검증한다. 즉 이 시스템을 추가해도 기존 서버 재검증 로직(/api/run/submit)은 손댈 필요가 없다 — 어떤 빌드로 깼든 "3라운드 깼다"는 사실만 중요하다.

업그레이드 시스템 이후 요청된 7가지를 정리한다. 전부 구현 전 — 첨삭을 받기 위한 초안이다. 명확한 버그는 바로 수정 방식을 확정해 적었고, 취향·밸런스가 걸린 항목은 기본안 + 열린 질문으로 남겼다.

1. 몹 원거리 공격 제안

지금은 몹 전원이 접촉 데미지만 준다 — 엄폐물이 플레이어 총알만 막는 게 비대칭적으로 느껴지는 이유이기도 하다. 유형별로 다른 원거리 공격을 붙이면 엄폐물이 양방향으로 의미를 가지게 된다.

유형원거리 공격(제안)특징
일반딱지 던지기짧은 사거리, 저데미지, 짧은 예열
탱크형돌멩이 던지기느린 투사체, 고데미지, 긴 예열(텔레그래프 필수)
스피드형고무줄 새총빠른 투사체, 저데미지, 예열 거의 없음(이동 중 발사 가능)
롤러형없음(기존 유지)방패·구르기 정체성이 이미 확실해서 원거리까지 더하면 과함
엘리트책장 넘기며 페이지 투척부채꼴 다발 투척, 긴 예열

공통 규칙(제안): 예열(telegraph) 있는 공격은 발사 전 짧게 깜빡이거나 커지는 연출로 "피할 시간"을 준다. 몹 투사체도 엄폐물에 막힌다 (플레이어 총알과 동일 규칙) — 그래야 은폐가 공수 양쪽에서 의미를 가진다.

라운드별 마릿수 증가

  • 제안: 1R 5~6 / 2R 7~8 / 3R 6~7+엘리트1

이동속도 전반 상향

🧨 폭탄돌리기(자폭몹) — 신규 유형

  • 빠르게 직진 추적(속도 110), 플레이어 반경 40px 이내 접근 시 예열 후 폭발(짧게 깜빡이다 터짐) — 광역 데미지를 입히고 자기 자신도 소멸
  • 총에 맞아 죽으면(폭발 전 사망) 그냥 죽는다 — 폭발 없음(단순화, 아래 열린 질문 참고)

아이템 드랍률 감소

  • 제안: 전부 ×0.7 (0.42/0.49/0.63, 보너스 0.25) — 재화량은 그대로, 아이템만 희석

3. 멀티샷 조준 버그 확정 — 버그 수정

원인 확인됨: computeFiringAngles()가 총알 개수가 짝수일 때 부채꼴을 정확히 좌우 대칭으로 벌려서, 정중앙(실제 조준각)에는 총알이 하나도 없다 — 2발일 때 -7.5°/+7.5°뿐이라 가운데 있는 타겟은 둘 다 빗나간다. 3발일 때는 우연히 가운데(0°)가 포함돼서 문제가 없었다.

수정 방식(확정): 총알 개수와 무관하게 항상 정확한 조준각(0°) 총알을 하나 포함시키고, 나머지 총알을 좌→우→좌→우 순서로 하나씩 덧붙인다 — 홀수 개일 땐 지금처럼 대칭 부채꼴이 되고, 짝수 개일 땐 가운데 하나 + 한쪽으로 치우친 나머지가 된다. 시각적 대칭성보다 "가운데 타겟은 항상 맞는다"는 기능적 정확성을 우선했다.

4. 플레이어 신규 공격 패턴(지뢰·자동포탑·투척) 제안 — 규모 큼

기존 발사 패턴계(고무줄 연사·쌍딱총·비석치기)는 전부 "메인 총알 발사" 파이프라인 하나를 건드리는 수준이었다. 이번 3개는 성격이 달라서 — 각각 자기만의 쿨다운·투사체·업데이트 루프를 새로 갖는 하위 시스템이다. 사실상 업그레이드 시스템 한 판 더 만드는 규모라고 보는 게 맞다.

💣 부비트랩(지뢰)

  • 일정 주기(예: 4초)마다 플레이어 발밑에 자동 설치, 적이 밟으면 폭발
  • 설치 개수 상한 필요(동시에 너무 많이 깔리지 않게) — 예: 최대 3개, 초과 시 가장 오래된 것부터 소멸

🏹 자동 딱총(보조 포탑)

  • 메인 총과 별개로, 자기 쿨다운으로 가장 가까운 적에게 자동 발사(플레이어 조작 무관)
  • 메인 총보다 약하게(예: 데미지 50%, 쿨다운 2배) — 보조 화력이지 대체가 아님

🎯 폭탄 던지기(투척)

  • 포물선으로 날아가 착지 지점에서 지연 폭발(광역) — 다수의 적을 상대로 유리
  • 자동 발사면 좋을지, 별도 키(예: Space)로 플레이어가 직접 던지게 할지는 열린 질문

5. 카메라 추적 + 월드 확장 제안

현재 CANVAS_W/H(960×540)가 화면 크기이자 월드 크기 그 자체다 — 그래서 좁게 느껴진다. 화면(뷰포트)은 그대로 두고, 월드만 키워서 카메라가 플레이어를 따라다니게 하는 안을 제안한다.

제안 수치

  • 월드 2400×1350(뷰포트의 2.5배), 뷰포트(960×540)는 그대로
  • this.cameras.main.setBounds(...) + startFollow(this.player, true, 0.1, 0.1)

같이 손봐야 하는 것

  • maps.ts의 4개 레이아웃 좌표가 전부 960×540 기준 — 월드가 커지면 좌표 재설계 필요(그냥 늘리면 엄폐물이 화면 구석에만 몰림)
  • 적 가장자리 스폰(randomEdgePoint)은 월드 크기 상수만 바꾸면 자동으로 대응됨

6. 업그레이드 캡슐 라벨 표시 확정 — UI 수정

지금은 캡슐에 "?"만 표시하고 열어야 정체가 드러나는 가챠 연출이었는데, 3장 다 무작위로 안 보이니 선택이 아니라 뽑기처럼 느껴진다는 피드백. 확정: 캡슐 위에 업그레이드 이름을 바로 표시해서 실제로 "골라서" 여는 방식으로 바꾼다 — 데이터는 이미 있다(UpgradeCard.name), UpgradeChoiceScene.buildCapsule()의 "?" 텍스트를 card.name으로 바꾸기만 하면 된다.

Design draft · not yet implemented · biggest architecture change so far

스테이지 셀렉트 시스템 — "1-1 ~ 1-10, 2-1 ~ 2-10..." (설계 초안)

가능하다 — 그리고 이 프로젝트에서 지금까지 한 것 중 가장 큰 구조 변경이다. 지금은 "런 하나 = 시드로 랜덤 결정된 3라운드"인데, 스테이지 셀렉트는 그 자리에 "챕터-스테이지 번호로 고정된, 맵·몹·난이도가 정해진 레벨"을 넣는 것이다. 구현 전 — 첨삭 대기. 다른 대기 중인 설계 초안(전투 다양화·월드 확장)과 어떤 순서로 할지도 열린 질문 중 하나로 남겨뒀다.

왜 이게 제일 큰 변경인가

지금까지의 확장(업그레이드 시스템, 몹 다양성 등)은 전부 feature/combat 한 영역 안에서 끝났다. 스테이지 셀렉트는 세 영역 전부를 건드린다 — 어떤 스테이지까지 깼는지 저장할 DB 컬럼(auth-backend), 스테이지를 고르는 화면(town-scene), 스테이지별로 다른 맵·몹·난이도를 실제로 트는 로직(combat). 지난번 업그레이드 시스템처럼 "combat 안에서 worktree 2개"가 아니라, 원래 3개 병렬 세션 구조 그대로 쓰기에 맞는 첫 확장이다.

총 챕터 수우선 2챕터(20스테이지)로 시작 — 이후 챕터 추가는 데이터만 늘리면 되는 구조로 설계(무한 절차생성 챕터는 스코프 밖)
잠금 해제선형 — 1-1부터 순서대로 클리어해야 다음이 열림. 클리어한 스테이지는 파밍용으로 자유 재도전 가능
스테이지 하나의 길이3라운드(변경 없음) — 지금까지 플레이·검증해온 것 전체가 사실상 "1-1"이었던 셈, 기존 라운드 구조를 그대로 스테이지 하나의 내용물로 재사용

스테이지 종료 후 흐름 확정

스테이지(3라운드) 클리어 시, 결과 화면 대신(또는 그 위에) 5초 타임아웃 다이얼로그를 띄운다 — "다음 스테이지로" / "마을로" 두 선택지, 5초 안에 입력이 없으면 자동으로 마을로 이동. 계속 이어서 플레이하고 싶은 사람은 굳이 마을을 거치지 않고 바로 다음 스테이지로 넘어갈 수 있고, 쉬고 싶으면 그냥 놔두면 알아서 안전하게 마을로 돌아간다.

맵·몹 배정 (제안)

맵

  • 기존 4개 레이아웃(빈 마당/상자더미/골목길/놀이터소품)을 스테이지 번호에 고정 순환 배정 (예: (스테이지 - 1) % 4) — "이 스테이지는 항상 이 맵"이라는 정체성이 생김
  • 지금처럼 시드로 매번 랜덤이면 스테이지 번호 자체의 의미가 옅어짐 — 스테이지 시스템 취지에 맞게 맵은 고정, 몹 배치·보상 굴림에만 시드를 계속 씀

몹·난이도

  • 전역 스테이지 인덱스((챕터-1)*10 + 스테이지)가 커질수록 마릿수·체력·공격력이 완만하게 계단식 상승하는 난이도 곡선 함수 하나로 관리
  • 챕터가 바뀌는 지점(예: 2-1)에서 한 단계 더 크게 상승 — "챕터가 바뀌었다"는 체감을 준다
  • 전투 다양화 초안의 몹 원거리 공격·자폭몹도 스테이지 번호에 따라 점진적으로 등장(예: 1-1~1-3은 기존 유형만, 1-4부터 자폭몹 등장, 2장부턴 전원 원거리 공격 보유)

영역별 작업 (제안 — 병렬 분배안)

auth-backend
  • TownProgress에 highestStageCleared Int @default(0)(또는 챕터·스테이지 분리 필드) 추가 — Prisma 마이그레이션 필요
  • POST /api/run/start가 stageId를 받아 그 스테이지 잠금 여부 서버에서 검증 후 seed 발급
  • POST /api/run/submit도 stageId를 같이 받아 그 스테이지 기준 재계산 — 서버 재검증 원칙(「시드 & 검증 로직 공유」)은 그대로 유지, 검증 기준만 "라운드 인덱스"에서 "스테이지+라운드"로 확장
town-scene
  • 스테이지 선택 화면 신설 — 챕터별 그리드(1-1~1-10, 2-1~2-10...), 클리어/잠김/현재 상태 표시
  • "런 시작" 버튼이 스테이지 미선택 상태로 있던 기존 흐름을 대체(또는 그 앞에 스테이지 선택 단계 하나 추가)
combat
  • game-logic/에 스테이지 난이도 곡선 모듈 신설(스테이지 인덱스 → 맵 인덱스·몹 스탯 배율·라운드 수를 결정하는 순수 함수) — 기존 runPlan.ts/maps.ts를 시드 전용에서 "시드 + 스테이지" 기반으로 확장
  • DungeonScene이 seed 대신(또는 seed와 함께) stageId를 받아 위 모듈로 라운드·맵·몹 구성을 결정

확정 — 첨삭 반영 완료

  • 스테이지당 라운드 수 — 3라운드(변경 없음, 위 참고)
  • 총 챕터 수 — 우선 2챕터(20스테이지)로 시작

Auth & security

인증 · 보안 설계

세션 쿠키

  • HttpOnly · Secure · SameSite=Lax (Auth.js 기본값)
  • Database 세션 전략 — 강제 로그아웃 가능

데이터 격리

  • Auth.js로 인증하므로 Supabase auth.uid()는 채워지지 않음 — 매 요청 트랜잭션에서 set_config('app.user_id', ...)로 세션 변수 세팅
  • RLS 정책은 app.user_id 기준으로 격리 (supabase/rls.sql, withUserContext.ts)
  • 클라이언트가 직접 쿼리해도 타인 데이터 접근 불가
