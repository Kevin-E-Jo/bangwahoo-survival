씬 지도 — 병렬 작업의 경계선

민트는 Next.js 페이지, 코랄은 Phaser 캔버스 안의 씬이다. 이 색 경계가 곧 작업을 나눌 수 있는 지점이다.

Next.js 페이지 Phaser 씬

라우트 & 경계 원칙

/login → /town → /play(Phaser 마운트, BootScene부터 시작) → 클리어·사망 시 다시 /town. Next.js와 Phaser는 같은 세션 쿠키로 인증되어 있으므로, 경계를 넘을 때 JS 객체를 직접 넘기지 않는다 — 각자 필요한 데이터를 서버 API로 다시 조회한다. 자세한 계약은 아래 「씬 간 인터페이스」 참고.

씬별 담당 — 병렬 작업 분배표

각 카드가 곧 하나의 작업 단위다. 옆 씬과 주고받는 데이터 계약만 지키면 독립적으로 진행할 수 있다.

TownScene /town

  • "런 시작" 버튼 → /play로 라우팅만 (데이터 전달 없음)
phaser

DungeonScene + UIScene

  • 발급받은 seed로 라운드별 적 수 결정(정확히 3라운드), 사선 탑뷰 WASD 이동 + 자동 조준·발사
  • UIScene은 launch()로 병렬 실행, combat:* 이벤트로 HUD 갱신
  • 종료 시 combat:run-ended 발행 → ResultScene 전환 (실패 시 소프트 페널티)
phaser

ResultScene

  • POST /api/run/submit로 runId+결과 제출, 서버가 seed로 재계산해 검증
  • 검증 통과분만 TownProgress에 반영, 화면엔 확정된 보상만 표시
  • 확인 버튼 → /town으로 이동 (재마운트 시 최신 진행도 재조회)

Contracts

씬 간 인터페이스

Next.js와 Phaser 사이에 JS 객체를 직접 넘기지 않는다. 아래 API로만 통신하고, 나머지는 각자 영역 안에서 해결한다.

엔드포인트호출 주체역할
GET /api/town/progressTownScene재화·무기 레벨·보유 파츠 조회
POST /api/town/upgradeTownScene업그레이드 구매 — 서버가 재화 검증 후 차감
POST /api/run/startBootScene서버가 seed 발급 — 클라이언트가 유리한 seed를 고르지 못하게 함
POST /api/run/submitResultSceneseed+결과 제출 → 서버가 동일 seed로 재계산해 검증 후 반영

Phaser 내부 이벤트 (DungeonScene ↔ UIScene)

UIScene은 launch()로 DungeonScene과 병렬 실행되므로, 씬 이벤트로만 통신한다.

이벤트페이로드의미
combat:hp-changed{current, max}HP 바 갱신
combat:ammo-changed{current, max}탄약 표시 갱신
combat:wave-started{waveIndex, totalWaves}웨이브 진행도 표시
combat:wave-cleared{waveIndex, loot}웨이브 클리어 연출·획득 표시
combat:run-ended{result, collectedItems, wavesCleared, elapsedMs}ResultScene 전환 트리거

시드 & 검증 로직 공유

라운드 구성(적 수)·보상을 seed로부터 결정하는 함수는 클라이언트(Phaser)와 서버(API route)가 같은 TypeScript 모듈을 import해서 써야 한다. 로직이 갈라지면 서버 재계산이 클라이언트 결과와 어긋나 정상 플레이도 검증에 실패할 수 있다.

Core loop

게임플레이 규칙

루프

  • 마을 ↔ 던전 순환형, 한 런 5–10분
  • 목표: 웨이브를 버티며 잡템(그 시절 장난감)·재화 파밍 → 마을에서 판매해 무기 업그레이드

전투

  • 고정 해상도 캔버스, PC 키보드 우선(마우스 불필요)

절차 생성

  • 적은 화면 가장자리에서 등장해 플레이어를 추적

실패 페널티

  • 소프트 페널티 — 해당 런 미반출 자원만 손실
  • 마을 진행도는 항상 유지

업그레이드 시스템 — 런 한정 빌드 강화 (설계 확정 · 구현 대기)

다른 로그라이크처럼, 런 진행 중에 강화를 골라 그 런만의 빌드를 만드는 시스템. 첨삭을 거쳐 세부까지 확정됐고, 아직 코드는 한 줄도 안 들어간 상태다. 마을에서 재화로 사는 영구 업그레이드(탄환 위력·탄창 용량)와는 완전히 별개이며, 런이 끝나면 초기화된다.

선택 시점 & 흐름 확정

기존에 이미 있는 라운드 클리어 흐름(combat:wave-cleared → 600ms 뒤 다음 라운드)에 선택 단계를 끼워 넣는다. 런당 3회로 확정 — 전투가 늘어지는 걸 피하려고 라운드 수를 늘리거나 라운드 중간 픽업을 섞지 않기로 함.

시점선택지비고
런 시작 직후3장 중 1장BootScene → DungeonScene 전환 직후, 첫 라운드 스폰 전에 삽입
1라운드 클리어 후3장 중 1장기존 clearCurrentRound()의 딜레이 지점에 끼워 넣음
2라운드 클리어 후3장 중 1장3라운드(엘리트 등장) 진입 직전 — 마무리 빌드 완성 지점

선택 UI가 뜨는 동안 DungeonScene은 scene.pause()로 정지, 선택 완료 시 재개 — 기존 UIScene과 같은 패턴(병렬 launch + 이벤트)으로 새 씬(가칭 UpgradeChoiceScene)을 추가하는 안을 제안한다. 연출은 그 시절 테마로 확정 — 평범한 카드 3장 나열이 아니라, 가챠캡슐(gacha_capsule 아이템으로 이미 있음) 3개가 놓여있다가 고른 캡슐이 열리며 내용물이 드러나는 식의 연출을 제안. 아트·애니메이션 작업이 추가로 필요하다.

카테고리 개요

발사 패턴계

멀티샷 · 더블샷 · 도탄

  • 총알이 나가는 방식 자체를 바꾼다 — 시각적으로도 가장 화려한 카테고리
스탯 강화계

데미지 · 공속 · 이동속도 · 탄창 · 재장전

  • 수치만 올라가는 안전한 카테고리 — 매 선택지 풀의 "무난한 선택"으로 항상 섞어 넣는다
속성탄계

폭죽탄(지속딜) · 물풍선탄(슬로우) · (확장 여지)

  • 명중 시 부가 효과 부여 — 적 데이터에 상태(status) 필드가 새로 필요한 유일한 카테고리

발사 패턴계 상세

이름은 이 프로젝트의 "그 시절" 톤에 맞춘 1차 초안 — 아이템 카탈로그의 구슬·팽이·요요·딱총처럼 실제 있던 놀이·문방구에서 따왔다. 마음에 안 들면 언제든 갈아엎어도 되는 부분.

고무줄 연사 Multishot

  • 발사할 때마다 총알 개수 +1, 부채꼴로 균등 확산(각도 간격 15°)
  • 스택 가능 — 최대 3회 중첩(기본 1발 → 최대 4발)
  • 확산이라 개별 총알 명중률은 떨어짐 — 물량으로 커버하는 방향

쌍딱총 Double Shot

  • 멀티샷과 달리 확산 없이, 같은 방향으로 정확히 겹쳐서 1발 더 발사(약 80ms 지연)
  • 스택 불가(유니크) — 명중률 손해 없이 화력만 2배가 되는 대신 흔치 않게
  • 고무줄 연사와는 서로 곱연산(스택마다 총알 수를 배로 늘리는 게 아니라 "동시 발사 세트" 자체를 한 번 더 쏘는 것)으로 상호작용 — 구현 시 발사 함수를 "이번에 만들 총알들의 각도 배열"로 리팩터링해두면 두 효과가 자연스럽게 합성된다

비석치기 Ricochet 확정

  • 총알이 엄폐물에 맞아도 파괴되지 않고 반사각으로 튕겨 계속 날아간다(전통 놀이 "비석치기"에서 이름을 땀) — 튕긴 뒤에도 적에게 명중하면 그대로 데미지
  • 스택 가능 — 스택마다 튕길 수 있는 최대 횟수 +1(최대 2스택 = 2회까지 튕김), 그 이상은 소멸
  • 구현 메모: 현재 physics.add.collider(bullets, obstacles, ...)가 무조건 bullet.destroy()하는 부분을, 이 업그레이드 보유 여부에 따라 반사(속도 벡터를 충돌면 기준으로 반사)로 분기해야 함

스탯 강화계 상세

전부 최대 5스택으로 상한 확정(런당 선택 기회가 3회뿐이라 사실상 초과할 일은 적지만, 안전장치로 둔다).

속성탄계 상세 확정

스택형으로 확정 — 폭죽탄·물풍선탄을 둘 다 들고 있으면 명중 시 화상+슬로우가 동시에 걸린다(서로 상쇄 없음, 각자 독립 적용). 같은 속성을 여러 번 고르면 그 속성 자체도 최대 3스택까지 중첩 — 스택마다 지속시간이 늘어난다(효과 강도 자체는 안 늘림, 무한 증식 방지).

🔥 폭죽탄 Fire

  • 명중 시 대상에게 화상 부여 — 초당 데미지 4, 기본 지속 3초(스택마다 +1초, 최대 5초)
  • 즉발 데미지는 그대로, 화상은 추가 지속딜 — 이미 화상 걸린 대상을 다시 맞히면 지속시간만 최댓값으로 갱신

💧 물풍선탄 Water

  • 명중 시 대상 이동속도 -40%, 기본 지속 2초(스택마다 +0.5초, 최대 3.5초)
  • 여러 발 맞혀도 지속시간만 갱신 — 감속률(-40%) 자체는 스택으로 안 늘림

확장 후보 속성 (미확정)

폭죽탄·물풍선탄 2종 확정 이후 추가로 나온 아이디어들 — 아직 어느 것도 채택 여부가 정해지지 않았다. 전부 넣어도 되고, 일부만 골라도 되고, 하나도 안 넣어도 된다. 서로 겹치지 않는 효과가 되도록 신경 썼다(불=지속딜 / 물=슬로우 / 아래는 각각 스턴·군집·중독 누적·추적 상실·도주로 전부 다른 종류).

⚡ 찌릿탄

  • 명중 시 인접 적 1체에게 50% 데미지로 연쇄
  • 비석치기(도탄)와 메커니즘이 비슷해 상호배타 여부 검토 필요

💨 바람개비탄

  • 명중 시 적을 밀어냄(넉백)
  • 엄폐물 쪽으로 밀어붙이면 흥미로운 조합이 될 수 있음

🧊 얼음땡탄

  • 명중 시 짧게(예: 1초) 완전 정지(스턴)
  • 물풍선탄(슬로우)의 상위호환처럼 보이지 않게, 확률 또는 지속시간을 크게 낮게 잡아야 함

🧲 자석탄

  • 명중 지점 주변의 다른 적들을 그 지점으로 끌어당겨 뭉치게 함
  • 고무줄 연사·비석치기 등 광역기와 조합했을 때 시너지가 커짐 — 조합 의존도가 높은 픽

🤢 불량식품탄

  • 명중 시 중독 부여 — 폭죽탄과 달리 맞을수록 중독이 누적되어 틱 데미지가 커짐(상한 필요)
  • 불(비누적) vs 독(누적)으로 같은 "지속딜" 카테고리 안에서도 성격이 다른 선택지가 됨

📸 플래시탄

  • 명중 시 잠깐 실명 — 적이 플레이어 추적을 잃고 무작위 방향으로 이동
  • 다른 속성이 전부 "더 세게 때리기"용이라면, 이건 유일하게 회피·카이팅에 어울리는 픽

📯 호루라기탄

  • 명중 시 몇 초간 플레이어 반대 방향으로 도주(넉백은 "한 번 밀기", 이건 "지속 도주"로 차별화)
  • 탱크형처럼 위협적인 몹을 일시적으로 무력화하는 용도로 특히 유용할 듯

아키텍처 통합 지점 (제안)

새 공유 모듈

  • src/lib/game-logic/upgrades.ts — 업그레이드 카탈로그(효과 수치·스택 규칙)를 순수 데이터로 정의. 기존 catalog.ts(아이템)와 같은 패턴
  • 선택지 3장을 뽑는 로직도 createRng(seed, "upgrades")로 시드 기반 결정론 유지 — 맵 레이아웃·몹 구성과 같은 원칙(「시드 & 검증 로직 공유」 참고)

DungeonScene 쪽 변화

  • 현재 적용된 업그레이드 목록을 씬 상태로 보유, tryFireAt()이 이 상태를 읽어 총알 생성 방식(개수·각도·튕김 여부)을 결정하도록 리팩터링 필요
  • 속성탄은 적 쪽에 상태 필드(예: burnUntil, slowUntil) 추가, update()에 상태 틱 처리 루프 하나 추가

서버 검증과의 관계

이 업그레이드들은 순수하게 런 안에서만 전투력에 영향을 준다 — 재화·아이템 보상은 여전히 roundsCleared(몇 라운드를 깼는지)만으로 결정되고, 서버는 그 값에 대응하는 보상만 재계산해 검증한다. 즉 이 시스템을 추가해도 기존 서버 재검증 로직(/api/run/submit)은 손댈 필요가 없다 — 어떤 빌드로 깼든 "3라운드 깼다"는 사실만 중요하다.

몹 난이도 상향 확정

업그레이드로 플레이어가 강해지는 만큼, 몹도 기본적으로 더 버텨야 손맛이 유지된다는 판단으로 함께 확정. 세부 배율까지 전부 정해짐 — 아래는 현재 구현된 ARCHETYPE_STATS(DungeonScene.ts) 기준 최종 변경값이다.

설계 확정 요약

이 문서에서 다뤘던 모든 열린 질문이 첨삭을 거쳐 확정됐다 — 선택 횟수(3회), 몹 난이도(체력·접촉데미지 ×1.5, 엘리트 ×1.75, 방어력 2 공통), 속성탄 스택형, 도탄은 엄폐물 튕김, 선택 UI는 그 시절 테마 연출, 스탯 강화계 5스택 상한, 업그레이드 이름은 그 시절 느낌으로. 남은 미확정 항목은 확장 후보 속성 7종(찌릿탄·바람개비탄·얼음땡탄·자석탄·불량식품탄·플래시탄·호루라기탄 — 채택 여부 자체가 미정) 중 무엇을 실제로 넣을지뿐이다.

Auth & security

인증 · 보안 설계

세션 쿠키

  • HttpOnly · Secure · SameSite=Lax (Auth.js 기본값)
  • Database 세션 전략 — 강제 로그아웃 가능

데이터 격리

  • Auth.js로 인증하므로 Supabase auth.uid()는 채워지지 않음 — 매 요청 트랜잭션에서 set_config('app.user_id', ...)로 세션 변수 세팅
  • RLS 정책은 app.user_id 기준으로 격리 (supabase/rls.sql, withUserContext.ts)
  • 클라이언트가 직접 쿼리해도 타인 데이터 접근 불가

  • ResultScene이 시드 + 결과를 제출
