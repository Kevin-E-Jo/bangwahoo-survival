# 하네스 엔지니어링 방법론

> 여러 Claude Code 세션(하네스)을 병렬로 돌려 이 프로젝트를 만들면서 실제로
> 효과가 있었던 설계·개발 원칙을 정리한 문서. 추상적인 조언이 아니라, 이
> 레포에서 실제로 적용한 사례를 근거로 삼는다. **새로운 설계·구현 결정을
> 내릴 때는 이 문서의 원칙과 어긋나지 않는지 먼저 확인한다.**

## 1. 작업 단위를 물리적으로 격리한다

병렬 에이전트가 같은 워킹 디렉터리를 공유하면 체크아웃 경합이 생긴다. 기능
단위로 git worktree를 분리해 각 에이전트가 자기 브랜치에 바인딩된 자기만의
디렉터리에서만 일한다.

- 적용: `feature/auth-backend`, `feature/town-scene`, `feature/combat` 각각
  전용 worktree. 루트 worktree는 `master`(통합 브랜치) 전용, 어떤 기능
  세션도 자기 작업을 여기 직접 커밋하지 않는다.

## 2. 공유되어야 하는 로직은 단일 진실 공급원 하나에만 둔다

여러 실행 환경(클라이언트/서버, 혹은 여러 소비자)이 같은 계산 결과에 합의해야
한다면, 그 로직은 정확히 한 곳에만 존재하고 양쪽이 그 모듈을 import해서 쓴다.
같은 로직을 두 번 구현하면 언젠가 반드시 갈라지고, 그 순간 정상적인 사용까지
검증에 실패하는 버그가 된다.

- 적용: `src/lib/game-logic/`(절차생성·보상 계산)가 Phaser 클라이언트와
  API 라우트 양쪽에서 동일하게 import된다. 이 폴더 밖에서 같은 로직을
  재구현하지 않는다는 규율을 README에 명문화해뒀다.

## 3. 클라이언트를 신뢰하지 않고, 서버가 독립적으로 재계산한다

보상·점수처럼 조작 가능성이 있는 상태는 클라이언트가 "이만큼 했다"고 주장하는
값을 그대로 믿지 않는다. 서버가 같은 시드·같은 로직으로 처음부터 다시
계산해서 비교한다.

- 적용: `/api/run/submit`이 클라이언트가 보낸 라운드 결과를 신뢰하지 않고,
  seed 기반으로 서버가 직접 재계산한 보상과 비교해 검증한다.

## 4. 절차 생성은 결정론적 시드 기반으로 만든다

같은 시드는 어떤 환경에서 실행하든 같은 결과를 내야, 원칙 2·3(공유 로직,
서버 재검증)이 성립한다. 순수 `Math.random()`이나 환경 의존 RNG를 절차 생성에
쓰지 않는다.

- 적용: `mulberry32` + FNV-1a 해시 기반 `createRng(seed, namespace)`. 노드맵
  선택, 보상 계산, 맵 레이아웃 선택이 모두 이걸 통해서만 난수를 뽑는다.

## 5. 통합 지점은 한 명(하나의 흐름)만 건드린다

여러 에이전트가 동시에 같은 통합 브랜치에 자유롭게 커밋하면 충돌·경합이
생긴다. 기본은 PR로만 통합하고, 통합 브랜치에 대한 예외적 직접 접근은 범위를
아주 좁게(파일 하나, 목적 하나) 명시적으로 사전 승인해서만 허용한다.

- 적용: `master`는 PR 머지로만 갱신. 유일한 예외는 `PORTFOLIO.md` 갱신
  — 사용자가 명시적으로 승인한, 딱 그 파일 하나에 대한 자동 push만 허용
  (각 worktree `CLAUDE.md` 참고). 그 외 어떤 것도 이 예외에 포함되지 않는다.

## 6. 큰 작업은 단계로 쪼개서, 단계마다 확인받고 넘어간다

요구사항이 여러 개면 한 번에 다 구현하고 결과만 보고하지 않는다. 순서를
제안하고, 한 단계 끝날 때마다 확인받은 뒤 다음으로 넘어간다. 중간에 방향이
잘못됐을 때 되돌릴 범위를 작게 유지하기 위해서다.

- 적용: "애니메이션 → 엄폐물/맵 → 몹 다양성" 순서를 먼저 제안하고 승인받은
  뒤, 애니메이션이 끝나자 다음 단계로 넘어가도 되는지 다시 확인받았다.

## 7. 실행해서 확인하기 전에는 "됐다"고 말하지 않는다

타입체크·린트 통과는 필요조건이지 충분조건이 아니다. 코드를 읽고 맞다고
판단하는 것과, 실제로 돌려서 그 상태를 관찰하는 것은 다르다. 환경이 검증을
방해하면(예: 자동화 브라우저 탭의 백그라운드 스로틀링) 검증 자체를 포기하지
않고 우회 방법을 만든다.

- 적용: 엄폐물 충돌을 커밋하기 전, 실제로 실행 중인 게임의 물리 엔진을
  직접 조작해(`game.loop.step()` 수동 프레임 진행) 플레이어/몹/총알이
  장애물에 실제로 막히는지 확인했다. 코드만 읽고 "블로킹 컬라이더를
  추가했으니 될 것"이라고 넘어가지 않았다.

## 8. 결정과 맥락을 살아있는 문서 하나에 남긴다

세션마다 컨텍스트가 끊기기 때문에, "왜 이렇게 했는지"가 코드에만 있으면
다음 세션(또는 다음 대화)이 그걸 다시 알아내야 한다. 아키텍처·결정·진행
상황을 한 문서에 계속 갱신해서, 다시 파고들지 않아도 되게 한다.

- 적용: `PORTFOLIO.md`(프로젝트 개요·구성·개발 로그)와
  `docs/blueprint.html`(팀 내부 설계/할 일)을 각각의 목적에 맞게 계속
  갱신한다. 어느 세션이 갱신하든 같은 문서 하나로 수렴한다.

## 9. 자율 실행 권한은 항상 좁고 명시적으로 사전 승인한다

에이전트가 사용자 확인 없이 스스로 실행해도 되는 범위를 넓게 잡지 않는다.
"이 파일 하나, 이 목적 하나"처럼 좁게 정의하고, 그 승인 자체를 사용자에게
명시적으로 확인받은 뒤에만 durable 설정(`CLAUDE.md` 등)에 기록한다. 승인
범위를 넘어서는 일반화(예: "문서 갱신이 허용되니 다른 정리 작업도
자동으로")는 하지 않는다.

- 적용: `PORTFOLIO.md` 자동 push는 사용자에게 방식을 직접 물어보고 승인받은
  뒤 `CLAUDE.md`에 기록했다. 다른 파일·다른 브랜치 작업에는 이 승인이
  적용되지 않는다고 각 `CLAUDE.md`에 명시했다.

## 10. 이상적인 도구가 없으면, 필요한 만큼만 직접 만든다

필요한 외부 도구(이미지 생성 등)가 없다고 결과물을 포기하거나 가짜로
때우지 않는다. 문제를 풀 수 있는 최소한의 도구를 직접 만들고, 그 위에서
작업한다.

- 적용: 이미지 생성 도구가 없어서 Node `zlib`만으로 PNG 인코더를 직접
  작성하고, 그 위에 사각형/타원 합성만으로 절차적 픽셀아트를 생성하는
  파이프라인을 구축했다.

## 11. 에이전트 간 통신은 명시적 채널로 하고, 상대 주장은 직접 검증한다

병렬 에이전트끼리는 서로의 내부 상태를 볼 수 없다. 조율은 메시지나 공유
파일 같은 명시적 채널로만 하고, 상대가 "이게 문제다"라고 보고해도 사실
여부는 직접 코드를 읽어 확인한 뒤 판단한다.

- 적용: 한 세션이 다른 세션의 파일이 특정 필드를 참조해서 머지하면 깨질
  거라고 주장했을 때, 실제 파일을 읽고 `grep`으로 확인해 사실이 아님을
  검증한 뒤 상대에게 정정을 전달했다.
